# Risk Assessment — TrialPilot

Scale (SOP CSV-001 §4): **H** — could corrupt a GxP record/signature, mislead a trial decision or hide a change (≥ 2 tests incl. a negative test); **M** — degrades decision quality, detectable (≥ 1 test); **L** — cosmetic/performance (test or justification).

Totals: H **21** · M **10** · L **1** · GxP-relevant **21** of 32

| Requirement | Area | Risk | Rationale | GxP | GxP rationale |
|---|---|---|---|---|---|
| **URS-001** The system imports a trial from ClinicalTrials.gov by NCT ID into a TrialDesign (sites, visits, enrollment, duration) and lists every field it could not obtain in missing_fields. | import | **M** | Wrong or silently missing design facts propagate into every planning metric. | no | Planning input; no GxP record is created from it directly. |
| **URS-002** Protocol-PDF extraction (LLM) returns candidate visits/procedures that a human must confirm before they enter a TrialDesign; nothing extracted is applied automatically. | import | **H** | AI extraction errors would enter the design unnoticed if applied without review. | yes | AI-generated content must stay a draft until a human accepts it (human in charge). |
| **URS-003** Every parameter in the library has low/mid/high values and either a source (title, URL, year) or assumption=true with a written rationale; invalid parameters are rejected at load. | parameters | **H** | An unsourced or mis-entered factor (e.g. a unit error) silently biases all results. | no | Affects decision support quality, not a GxP record. |
| **URS-004** Every computed metric (cost, site staff hours, patient travel hours, CO2e, duration, drug waste) is reported as a P10/P50/P90 range with a unit; a missing input is reported as missing, never zeroed. | engine | **H** | Point estimates or silent zeros overstate certainty and mislead trial design decisions. | no | Decision support output. |
| **URS-005** A computation is reproducible: the same design, levers, parameter-set version and seed give identical results. | engine | **H** | Approved scenarios must be re-creatable; non-determinism breaks review and audit. | yes | An approved scenario is a signed record; its numbers must be reproducible. |
| **URS-006** Each metric exposes its provenance: formula id, resolved inputs, parameter ids (with versions and sources) and assumptions used. | engine | **M** | Without provenance a reviewer cannot check a number before signing. | no | Supports review; not itself a record. |
| **URS-007** Design levers (remote monitoring share, home/remote visits, local labs, on-demand drug supply, removed procedures, excluded sites) change the affected metrics as documented in docs/model.md. | engine | **M** | A lever with no or wrong effect gives a false trade-off picture. | no | Decision support output. |
| **URS-008** Carbon follows the Low Carbon Clinical Trials Group module framework (module ids as published); drug_supply is flagged as an extension beyond the published method. | engine | **M** | Non-standard module mapping makes footprints incomparable with published ones. | no | ESG reporting metric. |
| **URS-009** Scenario compute with 2,000 Monte Carlo draws returns in under 300 ms at P50. | performance | **L** | Slowness hurts usability but not correctness. | no | Usability only. |
| **URS-010** Saved scenarios are versioned; a scenario that has been submitted for approval cannot be changed (an edit creates a new version). | records | **H** | Changing a record after submission would make signatures meaningless. | yes | Integrity of signed records (ALCOA+ — original, enduring). |
| **URS-011** Simulated operational data is labelled simulated in data (simulated=true), API responses and the UI ("Simulated feed" badge). | operations | **H** | Simulated data mistaken for real trial data would be a serious misrepresentation. | yes | Data provenance must be unambiguous. |
| **URS-012** Alerts carry a severity, a plain-English summary, estimated impact as ranges (cost, CO2e, delay, site hours) and recommended actions; every alert action (acknowledge, plan, dismiss with reason) is audited. | operations | **M** | Unexplained or unranged alerts lead to wrong prioritisation. | no | Operational decision support. |
| **URS-013** The effect of an intervention is estimated with difference-in-differences against control sites and reported with a range and a verdict (likely worked / inconclusive / likely coincidence / no effect). | operations | **M** | Attributing coincidence to an intervention misdirects future actions. | no | Operational decision support. |
| **URS-014** The science check reproduces the published CASPS and PRIMETIME trial footprints (BMJ Open 2024) and reports the % difference per module against the published values. | science | **M** | The carbon model's credibility rests on reproducing published results. | no | Model verification evidence. |
| **URS-015** The audit trail records every data-changing action with actor, role, UTC timestamp, action, object, before/after record hash and reason. | audit | **H** | Missing audit entries make changes untraceable (21 CFR 11.10(e)). | yes | Audit trail of GxP records. |
| **URS-016** The audit trail is append-only: the database rejects UPDATE and DELETE on audit entries and signatures, and no application code path updates or deletes them. | audit | **H** | An editable audit trail can hide record changes. | yes | Audit trail integrity. |
| **URS-017** The audit trail is tamper-evident: a SHA-256 hash chain links every entry and chain verification reports the first altered or missing entry. | audit | **H** | Tampering below the application (raw SQL) must still be detectable. | yes | Audit trail integrity. |
| **URS-018** Signing requires re-authentication with the signer's PIN (stored only as a peppered argon2 hash); a wrong PIN is rejected, three consecutive failures lock signing for 5 minutes, and failures and lockouts are audited. | esign | **H** | Weak signer authentication allows signatures by the wrong person (21 CFR 11.200). | yes | Electronic signature controls. |
| **URS-019** A signature records signer, printed name, UTC date/time and meaning, is bound to the hash of the exact record signed, and its manifestation is shown with the record and in exports (21 CFR 11.50). | esign | **H** | A signature without meaning/time/record binding is not attributable. | yes | Electronic signature manifestation and linking (21 CFR 11.50, 11.70). |
| **URS-020** If a signed record changes afterwards, its signatures are shown as invalid and the record cannot be signed further without resubmission. | esign | **H** | Signatures must not carry over to content the signer never saw. | yes | Signature/record linking (21 CFR 11.70). |
| **URS-021** The author of a record can never review, approve or reject their own record (segregation of duties). | workflow | **H** | Self-approval defeats independent review. | yes | Approval controls. |
| **URS-022** Approval steps are signed in the required order for each record type (e.g. reviewed then approved), one person signs at most one step, and only QA gives the final approval. | workflow | **H** | Out-of-order or single-person approvals bypass review. | yes | Approval controls. |
| **URS-023** Permissions follow the role matrix in validation/ROLES.md; a user's role comes from the user registry, never from the request, and mutations without an identity are rejected. | access | **H** | Trusting a client-supplied role would let anyone act as QA. | yes | Access control (21 CFR 11.10(d), (g)). |
| **URS-024** A test protocol must be approved (exact version) before tpv executes it; tpv refuses otherwise and says why. | validation | **H** | Executing unapproved protocols produces evidence nobody agreed to. | yes | Validation lifecycle control. |
| **URS-025** AI may draft prose but never writes results, evidence, counts or signatures; AI-drafted text is stamped "DRAFT — requires human review" and AI actors cannot sign. | validation | **H** | AI-written results or signatures would be fabricated evidence. | yes | Humans stay accountable for GxP decisions. |
| **URS-026** Test execution evidence is captured with a manifest listing the sha256 of every evidence file, UTC timestamps, the executor and the git commit, and is signed "executed" by the executor. | validation | **H** | Unhashed evidence can be altered after the fact. | yes | Evidence integrity. |
| **URS-027** The traceability matrix links every requirement to its risk, tests, results and evidence hashes, and flags requirements with no test and tests with no requirement. | validation | **H** | Untested requirements would otherwise pass unnoticed. | yes | Validation completeness. |
| **URS-028** Exports (audit trail CSV, scenario CSV) contain every row of the underlying data, none dropped. | records | **H** | A truncated export misrepresents the record to inspectors. | yes | Accurate and complete copies of records (21 CFR 11.10(b)). |
| **URS-029** With DEMO_OFFLINE=1 the system makes no external network calls, uses cached fixtures, and reports offline=true on /api/health; the documented default is DEMO_OFFLINE=0. | configuration | **M** | A wrong offline setting breaks the demo or leaks calls to external services. | no | Configuration of a demo mode. |
| **URS-030** Secrets (API keys, the PIN pepper) come only from the environment / .env, which is never committed; .env.example lists names only. | configuration | **M** | Leaked keys or pepper compromise the system and signature controls. | yes | Protects the signature credential store. |
| **URS-031** For a code change, change control lists the changed files, the affected requirements (via the component map) and the tests to rerun, and drafts a change record that a human completes and that is approved reviewer → QA. | validation | **M** | Unassessed changes can silently break validated behaviour. | yes | Change control of a validated system. |
| **URS-032** The validation summary report states the real counts from the signed execution (tests, requirement results, deviations) and shows "awaiting QA approval" until QA signs it; QA's signature is invalidated if the report changes. | validation | **H** | An optimistic or edited report would misstate the validation outcome. | yes | Validation summary report is a GxP record. |
